# ChargeHub 从整到细：项目怎么运转

这份文档按「从上到下」来讲：先看整套系统像什么，再看四个程序怎么配合，再看一次点击怎么走到数据库，最后才进入每个模块里的函数。

假定你还不太熟 Qt / TCP / SQLite。遇到术语会先用大白话解释一句。

更短的架构表见 `docs/概要设计说明书.md`。报文字段见 `protocol/messages.md`。  
**每张表、每个字段**：`database/schema.sql`（列后面都有注释）。  
**每个 C++ 函数**：打开对应 `.h`，再对照 `.cpp` 函数上一行。

---

## 1. 这套系统在干什么

ChargeHub 是一个**充电桩管理系统**，对应课程里的「用户端—服务端—数据端—决策端」：

| 谁 | 他想干什么 |
|----|------------|
| 车主（用户端） | 登录、找附近电站、预约、充电、付钱、评价 |
| 运营（管理端窗口） | 看营收、管电站和电桩、冻结用户、代结算、看分析 |
| 领导看大屏（浏览器） | 只看图表，不改任何账 |
| 预测脚本 | 根据历史订单估计以后忙不忙，只写「分析表」 |

整套东西**必须先开管理端**。管理端既是运营界面，也是全组唯一的服务器：别人的用户端都连它，账本也只在它那一台电脑上。

## 2. 电脑上实际开的是哪几个程序

打开以后，你通常会看到三类窗口。它们是**四个程序**（有一个没窗口）：

```
┌─────────────┐     网线/局域网      ┌──────────────────────────┐
│  用户端 App │  ─ ─ ─ 端口 8888 ─ ► │ 管理端（服务器 + 运营窗）  │
│ userclient  │                      │ adminserver               │
└─────────────┘                      │   ├─ 运营界面 MainWindow  │
                                     │   ├─ 听电话 TcpServer     │
                                     │   └─ 账本 SQLite 文件     │
                                     └────────────┬─────────────┘
                                                  │ 只读同一份文件
                     ┌─────────────┐              │
                     │ 浏览器大屏   │ ◄── HTTP 5000┤
                     │ dashboard   │              │
                     └─────────────┘              │
                     ┌─────────────┐              │
                     │ 预测脚本     │ 只写分析表 ──┘
                     │ ml/forecast │
                     └─────────────┘
```

用生活类比：

- **管理端** = 充电站总部：账本锁在保险柜里，前台电话是 8888。
- **用户端** = 车主手机 App：只能打电话，不能自己改保险柜。
- **大屏** = 会议室电视：插总部的账本复印件，只看不改。
- **预测脚本** = 分析员：可以在账本后面贴「预测便签」，但不能改余额。

为什么用户端不许直接打开数据库？两台电脑各改各的文件，今天的钱对不上、桩状态也会乱。所以**全组联调只允许一台电脑开管理端**。

## 4. 几个必懂的小概念

**TCP**：两条程序之间的一根「电话线」。管理端先听 8888，用户端再拨号。线断了，电话就打不通。

**JSON**：双方约定的「小纸条」格式，例如 `{ "type": "LOGIN", "data": { "phone": "138..." } }`。人能看懂，程序也好解析。

**长度前缀帧**：TCP 传来的是一串字节，可能把两张纸条粘在一起。所以先写 4 个字节表示「后面有多长」，再写 JSON。这就是 `Protocol`。

**token**：登录成功后总部发的临时通行证。之后每次请求都要带上。过期或账号被冻，通行证作废。

**事务**：开充要同时「插入订单 + 把桩改成在用」。两步要么都成功，要么都撤销，避免桩占了但没有订单。

**元和分**：界面和接口仍说「12.80 元」。内部加减用「整数分」，避免 0.1+0.2 那种小数误差差出 1 分钱。

## 5. 一条完整故事：从「点开充」到写进账本

先把这条故事记熟，后面每个函数都是其中一环。

```
用户点「开始充电」
    → UserWindow::tryStart
        先问有没有未完成订单（CHARGE_STATUS）
        没有才真正开充（START_CHARGE）
    → Client::request
        把 type/data/token 交给 Protocol::pack
        从网线发给管理端
    → TcpServer 收到字节
        Protocol::append 拆出一张完整 JSON
        调用 Dispatch::handle
    → Dispatch::handle
        认出 type = START_CHARGE
        用 token 找到用户（requireUser）
        调用 startCharge
    → Dispatch::startCharge
        查 openOrder、余额、桩是否闲着
        Database::transaction 里：插入订单，桩改「在用」
        calcLive 算出当前电量费用
        publicOrder 拼成回给手机的字段
    → TcpServer 把回包装回网线
    → Client 拆包，发出 responded 信号
    → UserWindow::onResp 刷新充电页
```

之后充电还在继续：

- 管理端每 5 秒 `TcpServer::pushChargeTicks` → `Dispatch::chargePushFor` → 再算一遍 `calcLive` → 推 `PUSH_CHARGE`。
- 用户端也可以 `pollCharge` 发 `CHARGE_STATUS`（给旧客户端留的路，字段不删）。

停充、结算是同一条管道，只是 `handle` 换成 `stopCharge` / `settle`。

运营人员在管理端点「代结算」**不走 8888**：`MainWindow::forceSettle` 直接调 `Dispatch::forceSettleOrder`，因为运营窗口和服务器是**同一个进程**，再给自己打电话多此一举。

## 6. 开机顺序（管理端 main.cpp）

1. 套上统一外观 `ChargeHubStyle`。
2. 用文件锁 `chargehub.lock`：同一台机器不能开第二份管理端。
3. `Database::open`：打开（或创建）`data/chargehub.db`，建表、补列、必要时灌演示账号。
4. 创建 `Dispatch(&db)`：业务对象，构造时 `loadSessions` 把没过期的登录恢复回来。
5. 创建 `TcpServer(&dispatch)` 并 `listen(8888)`：**登录框还没点确定，8888 已经在听**，方便自动烟测。
6. 弹出运营登录框（演示 `admin` / `123456`）。
7. 通过后打开 `MainWindow`，底栏显示「用户端请填 xx.xx.xx.xx:8888」。

用户端 `main.cpp` 简单得多：套样式，打开 `UserWindow`。**绝不** `Database::open`。

## 7. 通信模块：Protocol（common）

**它只做一件事**：把一张 JSON 小纸条装进信封，或从粘在一起的信封里拆出来。不管登录成不成功，不管该收多少钱。

| 函数 | 谁调用 | 做什么 |
|------|--------|--------|
| `pack(json)` | `Client::request`、`TcpServer` 回包/推送 | 先写 4 字节大端长度，再写 JSON 正文 |
| `append(字节)` | 套接字 `readyRead` | 把刚读到的字节接到缓冲区末尾，再试着拆 |
| `tryDecode()` | `append` 内部 | 缓冲区够 4 字节就读长度；长度 0 或大于 1MB 丢掉（防坏包）；够一整包就解析成 JSON 放进队列 |
| `hasPacket` / `nextPacket` | 收包循环 | 问有没有拆好的包，取走下一张 |

管理端运营窗口**不用** Protocol，因为它不打电话给自己。

## 8. 用户端：Client（打电话的人）

`Client` 是 UserWindow 手里唯一的网线。

| 函数 / 信号 | 作用 |
|-------------|------|
| `connectTo(host, port)` | 拨号。地址来自登录页，自测填 `127.0.0.1:8888` |
| `request(type, data, token)` | `seq` 加 1，组成规定格式，`pack` 后写出。没连上只报错，不写半包 |
| `isConnected` | 线通不通 |
| 信号 `connected` | 拨通了。UserWindow 可能紧接着 `sendPendingAuth` 补发登录 |
| 信号 `responded` | 拆出一张完整回包（普通响应或 `PUSH_CHARGE`） |
| 信号 `failed` | 断线或系统错误，界面提示，不改账 |

它**没有**「开充」函数。开充只是 `request("START_CHARGE", {pileId}, token)`。

## 9. 用户端：UserWindow（所有页面）

界面分两层：

- `root_`：第 0 页登录，第 1 页主壳（左边导航 + 右边内容）。
- `pages_`：主壳里的找站、桩列表、充电、订单、评价、预约、我的。

`buildLogin` / `buildHome` / … 只负责把控件摆出来。真正办事的是下面这些。

### 9.1 登录注册

| 函数 | 做什么 | 接着谁 |
|------|--------|--------|
| `doLogin` | 检查手机号、密码长度，记下要发 LOGIN | 已连接则 `sendPendingAuth`，否则 `reconnect` |
| `doRegister` | 还要检查两次密码一致 | 同上，type 换成 REGISTER |
| `reconnect` | `client_.connectTo(serverHost, serverPort)` | 连上后 `sendPendingAuth` |
| `sendPendingAuth` | 把挂起的手机号密码发出去 | 回包进 `onResp` |
| `showShell` | 登录成功切到主壳 | `applyUser` 刷新头像余额 |

### 9.2 找站、开充、预约、评价

| 函数 | 发出的 type | 回包后谁画界面 |
|------|-------------|----------------|
| `queryStations` | `QUERY_STATIONS` | `renderStations` |
| 点进某站 | `QUERY_PILES` | `renderPiles` |
| `tryStart` | 先 `CHARGE_STATUS`，没有未完成单再 `START_CHARGE` | `showCharge` |
| `doReserve` / 取消 | `RESERVE_PILE` / `CANCEL_RESERVE` | 再拉桩或预约列表 |
| `submitReview` | `REVIEW_STATION` | `renderPileReview` |
| `pollCharge` | `CHARGE_STATUS` | `showCharge` |

`tryStart` 为什么先查状态？防止你口袋里已经有一笔没结的单，再开一笔。服务端 `startCharge` 也会再拦一次。

### 9.3 总调度 `onResp`

所有回包、包括推送，都进这一个函数：

1. `code != 0`：弹提示。只有登录/注册失败才退回登录页，别的失败不踢人。
2. 按 `type` 分支：`LOGIN` 存 `token_`；`PUSH_CHARGE` / `CHARGE_STATUS` 刷新充电；`SETTLE_ORDER` 跳订单页，等等。

### 9.4 不管账的功能

换头像、改昵称、充值、注销：仍然只发 `UPDATE_PROFILE` / `RECHARGE` / `CLOSE_ACCOUNT`。  
地图导航 `showStationLocation` 是用户端自己访问腾讯位置服务（静态图、路线、天气），**不经过** Dispatch，也不改订单。管理端刷新预测时用同一套 Key 拉实况天气；找站本地对不上才走地址解析。失败则回退模拟天气 / 中关村一带检索。

### 9.5 其余界面函数（只摆控件或只刷新，不写账）

| 函数 | 作用 |
|------|------|
| `buildLogin` / `buildShell` / `buildHome` / `buildPiles` / `buildCharge` / `buildOrders` / `buildMe` / `buildPileReview` / `buildReservations` | 把各页控件摆出来，按钮再接到上面那些槽 |
| `switchTab` | 左边导航切 `pages_`；进订单/预约页会再拉一次列表 |
| `applyUser` / `showAvatar` / `refreshMe` / `pickAvatar` / `clearAvatar` | 刷新顶栏余额头像；换头像只发 `UPDATE_PROFILE` |
| `renderStations` / `renderPiles` / `renderOrders` / `renderRecharge` / `renderReservations` / `renderPileReview` / `showCharge` | 把 JSON 画成卡片，不改库 |
| `openPileReview` / `setReviewStars` | 切到评价页、点亮星星 |
| `openNav` / `queryTencentRoute` | 浏览器导航 / 问腾讯路线时间和距离 |
| `coord` / `serverHost` / `serverPort` | 当前定位、登录页填的 IP 和端口 |
| `clearBox` | 重新画列表前清空布局 |

头文件 `userwindow.h` 里每个函数都有对应注释。

## 10. 管理端接入：TcpServer

可以想成总部前台：听电话、把纸条递给业务经理 Dispatch、把回条读给对方听。前台自己不算钱。

构造时启动一个 5 秒定时器，到期调用 `pushChargeTicks`。

| 函数 | 何时发生 | 做什么 | 找谁帮忙 |
|------|----------|--------|----------|
| `incomingConnection` | 用户端拨进来 | 新建套接字和 `Protocol`；有数据就拆包、`handle`、写回；能认出用户就 `bindUser` | `Dispatch::handle`、`userIdOfToken` |
| `bindUser` | 登录成功或请求带了有效 token | 记下「这根线属于用户 3」；若他正在倒计时释放，则取消倒计时 | — |
| `userStillOnline` | 判断断线前 | 这个用户是否还有别的线（一个人可能开两个用户端） | — |
| `scheduleRelease` | 一根线断了，且他已经没有别的线 | 开始 60 秒倒计时 | 到点仍离线 → `Dispatch::releaseStaleSession` |
| `pushChargeTicks` | 每 5 秒 | 给每个在线且「充电中」的用户推一帧 | `Dispatch::chargePushFor` |

推送的 `seq` 固定为 0。旧用户端如果不认识 `PUSH_CHARGE`，可以忽略，继续用轮询。

## 11. 业务中枢：Dispatch（最重要）

所有「准不准、扣多少钱、桩忙不忙」都在这里。界面和 TcpServer 只把参数递进来。

它有**两扇门**：

```
用户端 JSON ── handle() ─┐
                          ├─► startCharge / settle / listPiles …
运营按钮直接调用 ────────┘
```

### 11.1 总入口 `handle`

1. 取出 `type`、`seq`、`token`、`data`。
2. 若是开充/停充/结算/充值/预约这类**会改账**的操作：用 `token|type|seq` 查 8 秒缓存。短时间重复点，直接把上次结果再寄回去（防双击开两单）。
3. `LOGIN` / `REGISTER` 不需要旧 token；其它请求先 `requireUser`。
4. `switch(type)` 调到具体函数，再用 `ok` / `fail` 包成统一回包。

`ok` / `fail`：只是填 `code、message、data`，不写库。

### 11.2 登录和通行证

| 函数 | 作用 |
|------|------|
| `issueToken` | 做一串随机通行证，记内存，并写入 `session` 表（管理端重启后 30 分钟内还能用） |
| `loadSessions` | 进程启动时从 `session` 表读回来 |
| `persistSession` / `forgetSession` | 写入 / 删除表里的一行 |
| `userIdByToken` / `userIdOfToken` | 通行证换成用户编号；过期或没有则 0 |
| `requireUser` | 没登录、冻结、注销则失败，成功则返回用户行 |
| `dropUser` | 冻结或注销时，作废这个人所有通行证 |
| `publicUser` | 回给用户端看的字段（余额、昵称、头像），不含密码哈希 |

管理端自己的登录是 `adminLogin` / `adminRegister`，查的是 `admin` 表，**不是**用户表，也不走 8888。

### 11.3 找站、充电、结算（主路径）

| 函数 | 被谁叫 | 关键步骤 | 再调用 |
|------|--------|----------|--------|
| `queryStations` | handle | 按地址/半径找站 | 地图匹配（管理端内） |
| `queryPiles` | handle | 列出某站的桩，标出是否被预约 | `expireReservations`、`pileIsIdle` |
| `openOrder` | 多处 | 查该用户「充电中或待结算」的那一单 | 只读 SQL |
| `pileIsIdle` | 开充/预约 | 桩是闲置，且没有别人的有效预约（或预约就是你） | `activeReserve` |
| `startCharge` | handle | 有未完成单 / 没钱 / 桩不闲 → 拒绝；否则事务里下单、桩改在用 | `calcLive`、`publicOrder` |
| `chargeStatus` | handle、用户开充前 | 取出未完成单，再算一遍当前费用 | `calcLive` |
| `stopCharge` | handle | 充电中→待结算，写下电量和钱，桩回闲置 | `calcLive`、事务 |
| `settle` | handle | 待结算→已完成，按分扣余额 | 事务 |
| `calcLive` | 上面这些 + 推送 | 见下一小节 | 读 `tariff_rule` |
| `publicOrder` | 回包前 | 旧字段原样保留，再并上 live 里的新可选字段 | — |
| `chargePushFor` | TcpServer 定时器 | 给推送用的同一套订单快照 | `chargeStatus` 同类逻辑 |
| `releaseStaleSession` | TcpServer 断线超时 | 视同停充：待结算、释放桩、审计写「断线释放」 | 类似 `stopCharge` |

**`calcLive` 怎么算钱（答辩常问）**

1. 充电时长 = 现在（或已停充的结束时间）− 开始时间。
2. 电量 ≈ 桩的功率（kW）× 小时。
3. 若该站有分时电价表：按每个整点切开，这一小时用谷/平/峰那个单价。
4. 每一段：费用（分）= 电量 × 单价，先加成整数分，最后再换成元。
5. 回包里的 `amount`、`energyKwh` 仍是元和度；另外可带 `currentPrice`、`tariffLabel`。旧客户端不认识后两个，也不影响结算。

### 11.4 预约、评价、个人

| 函数 | 作用 |
|------|------|
| `expireReservations` | 过期预约标 `no_show`，别人就能用这根桩 |
| `reservePile` / `cancelReserve` | 预约 / 取消 |
| `reviewStation` | 必须有文字评价；顺带做很浅的关键词情感分析，写入评价相关表 |
| `listOrders` / `listRecharge` / `listReservations` / `listPileReviews` | 列表查询 |
| `recharge` | 模拟充值，单笔不超过 10000 元，事务入账 |
| `updateProfile` | 改昵称或头像（头像压成小 JPEG 存 BLOB） |
| `closeAccount` | 账号标「注销」，历史订单留下，同一手机号不能再注册 |

### 11.5 运营窗口用的函数（不经 Socket）

## 12. 账本：Database

只有管理端进程里的这一个对象负责**写入**业务表。

| 函数 | 作用 |
|------|------|
| `open` | 打开文件；`CREATE TABLE IF NOT EXISTS`；旧库缺列就 `ALTER`；没有演示数据就灌一份。已有联调库不会被清空 |
| `query` | 多行 SELECT |
| `one` | 只要第一行，没有则空 |
| `execute` | INSERT/UPDATE/DELETE；成功时 INSERT 返回新 id |
| `transaction(fn)` | 先 BEGIN，`fn()` 返回 true 才 COMMIT，否则 ROLLBACK |

`query` / `execute` 都加锁，避免界面线程和网络线程同时写坏文件。

大屏用 Python 再打开**同一份文件**，模式是只读查询。SQLite 开了 WAL，允许「一个人写、多个人读」。

## 15. 数据库里有哪些表（和谁有关）

列级说明以 `database/schema.sql` 为准（每个字段后面都有注释）。这里用「谁能写」把表和模块钉在一起，并列出每张表干什么、有哪些关键列。

| 表 | 干什么 | 谁写 | 谁读 |
|----|--------|------|------|
| `admin` | 运营账号 | Dispatch 注册/登录 | 仅管理端 |
| `user` | 车主、余额、状态 | Dispatch | 大屏可数人数 |
| `user_avatar` | 头像二进制 | Dispatch | 用户端回包带 Base64 |
| `station` / `pile` | 站和桩 | Dispatch | 用户端经接口、大屏直接读 |
| `charge_order` | 充电订单 | **仅** Dispatch | 大屏、预测只读已完成单 |
| `recharge_log` | 充值流水 | Dispatch | 用户端列表 |
| `reservation` | 预约 | Dispatch | 用户端 |
| `station_review` / `review_doc` | 评价与情感文本 | Dispatch | 用户端、分析页 |
| `tariff_rule` | 分时电价 | Dispatch（启用分时/采纳调度） | calcLive、大屏 |
| `session` | 通行证落库 | Dispatch | 仅管理端启动恢复 |
| `audit_log` | 运营留痕 | Dispatch | 管理端审计页 |
| `load_forecast` / `hourly_load` / `fault_risk` / `analysis_alert` / `dispatch_plan` / `analysis_report` | 预测与建议 | Dispatch.refreshForecast 或 ml 脚本 | 管理端分析页、大屏 |

### 15.1 每张表的字段（答辩对着 schema 讲）

**admin**：`id` 编号；`username` 登录名；`password_hash` SHA256；`created_at` 注册时间。与 `user` 完全分开。

**user**：`phone` 登录手机；`nickname` 显示名；`avatar_path` 空或 `db`；`password_hash`；`balance` 余额（元）；`status` 正常/冻结/注销；`address`/`loc_lat`/`loc_lng` 找站定位；`close_reason`/`closed_at` 注销留档。

**user_avatar**：`user_id` 一对一；`mime`；`data` 压缩图；`updated_at`。

**station**：`name`/`address`/`lng`/`lat`；`price_per_kwh` 基准电价（没有分时规则时用它）。

**pile**：`pile_no` 对外桩号；`station_id`；`type` 快充/慢充；`power_kw` 计费用；`status` 闲置/在用/故障；`total_charge_count`/`total_charge_minutes` 累计；`last_seen_at`；`fault_code`/`fault_at`。

**charge_order**：`order_no`；`user_id`/`pile_id`；`status` 充电中/待结算/已完成/已取消；`start_time`/`end_time`；`energy_kwh`/`amount` 停充后由 calcLive 写入。

**recharge_log**：`user_id`；`amount` 元；`result`；`created_at`。

**audit_log**：`actor` 谁（admin/system）；`action` 做什么；`target` 对谁；`result`；`created_at`。

**reservation**：`user_id`/`pile_id`；`status` 有效/已取消/已履约；`expire_at`；`no_show` 超时未到。

**station_review**：`score` 1~5；`comment` 必填文字；`pile_id` 评哪根桩。

**review_doc**：同一用户对同一桩一行，给情感统计。

**tariff_rule**：`start_hour` 含、`end_hour` 不含；`price_per_kwh`；`label` 谷/平/峰。

**session**：`token` 主键；`user_id`；`updated_at`。重启后 30 分钟内仍可用。

**load_forecast**：`horizon_hours` 1/6/24；`pred_kwh`；`pred_idle`；`peak_hour`。

**hourly_load**：某站 0~23 点预计电量。

**fault_risk**：`pile_no`/`station`/`score`/`level`/`reason`。

**analysis_alert**：`level`/`title`/`detail`。

**dispatch_plan**：`recommend` 建议；`priority`；`adopted`/`adopted_at` 是否被运营采纳。

**analysis_report**：`model_version`/`mae`/`rmse`/`sample_n`/`weather`。

两道「安全带」（部分唯一索引）：

- 一个用户不能同时有两笔「充电中或待结算」。
- 一根桩不能同时有两笔「充电中」。

代码里 `openOrder` / `pileIsIdle` 会先检查；库再挡一层，防止并发插进去。

**状态机（答辩画图用）**

```
电桩：  闲置 ──开充──► 在用 ──停充/断线/代停──► 闲置
              └──运营标故障──► 故障 ──恢复/重启──► 闲置

订单：  （无）──开充──► 充电中 ──停充/断线──► 待结算 ──结算──► 已完成
```
