# ChargeHub 模块与协作说明（答辩 / 联调用）

一句话：业务只在管理端 `Dispatch` 里改库；用户端只发 Socket；大屏只读 HTTP。

## 1. 进程怎么拼在一起

```
用户端 UserWindow ──Client──► Protocol 帧 ──► TcpServer ──► Dispatch ──► Database(SQLite)
运营窗口 MainWindow ───────────────────────────► Dispatch ──┘
Web 大屏 Flask ──────────────────────────────────────────► 只读同一份 .db
预测 ml/forecast.py ─────────────────────────────────────► 只写分析表
```

| 模块 | 进程 | 做什么 | 不做什么 |
|------|------|--------|----------|
| `common/protocol` | 用户端 + 管理端 | 把 JSON 编成「4 字节长度 + 正文」，粘包时再切开 | 不判断登录、不算钱 |
| `userclient/Client` | 用户端 | 连 `IP:8888`，发请求、收响应/`PUSH_CHARGE` | 不打开 `.db` |
| `userclient/UserWindow` | 用户端 | 登录、找桩、充电、评价、导航弹窗 | 不写余额/桩状态 |
| `adminserver/TcpServer` | 管理端 | 听 8888、拆包、回包、断线 60s 释放、5s 推送 | 不写业务 SQL |
| `adminserver/Dispatch` | 管理端 | **唯一业务规则**：登录、充电、结算、预约、资费 | 不管界面怎么画 |
| `adminserver/Database` | 管理端 | 唯一写库：查询 / 执行 / 事务 | 用户端、大屏不得再开一份写 |
| `adminserver/MainWindow` | 管理端 | 运营表格和按钮，同进程调 Dispatch | 不经 8888 再连自己 |
| `dashboard/app.py` | 独立 Flask | `GET /api/*` 给 ECharts | 不改订单、余额、桩状态 |
| `ml/forecast.py` | 脚本 | 算负荷预测 | 只动分析表 |

## 2. 一次「开充」怎么走

1. 用户点开充 → `UserWindow::tryStart` 先发 `CHARGE_STATUS`（有未完成单则拦住）。
2. 再发 `START_CHARGE` → `Client::request` → `Protocol::pack`。
3. `TcpServer` 拆包 → `Dispatch::handle` → `startCharge`。
4. `startCharge` 查 `openOrder`、余额、桩是否闲置，事务里插订单、桩改「在用」。
5. 回包 `publicOrder`（含 `calcLive` 的电量费用）。
6. 之后 `PUSH_CHARGE`（5s）或用户端轮询 `CHARGE_STATUS` 都只读 `calcLive`，不改接口旧字段。

停充 / 结算同理：`stopCharge` 把状态改成待结算；`settle` 按分扣余额、桩回闲置。

## 3. 各模块原理（答辩可按此讲）

### 3.1 Protocol（`common/protocol.*`）

- **原理**：TCP 是字节流。先写 4 字节大端长度，再写 JSON。收的时候先凑齐 4 字节读长度，再等正文；长度 0 或 >1MB 丢弃，防止坏帧。
- **谁用**：`Client` 发送；`TcpServer` 每连接一个 `Protocol` 实例拆包。管理端 GUI **不走** 这里。

### 3.2 Client / UserWindow

- **原理**：界面只拼 `type + data + token`。`seq` 自增。回包进 `onResp`，按 `type` 刷新对应页。
- **协作**：登录成功存 `token_`；充电页靠 `PUSH_CHARGE` 和 `pollCharge` 两路刷新，旧逻辑仍可用。

### 3.3 TcpServer

- **原理**：`incomingConnection` 里 `readyRead` → 拆包 → `handle` → 写回。登录成功或带 token 的请求调用 `bindUser`。
- **断线**：该用户最后一个 socket 断开后 60s 定时器；到点仍离线则 `releaseStaleSession`（充电中→待结算）。
- **推送**：5s 扫在线用户，充电中则发 `PUSH_CHARGE`（`seq=0`）。

### 3.4 Dispatch

- **两路入口**：Socket 走 `handle`；运营窗口直接调 `adminLogin` / `listPiles` / `forceSettleOrder` 等。
- **会话**：`issueToken` 写入内存和 `session` 表，30 分钟；启动 `loadSessions`。冻结/注销 `dropUser`。
- **幂等**：开充/停充/结算/充值/预约，8 秒内相同 `token|type|seq` 回缓存，防止重复点。
- **计费**：`calcLive` 按小时切段，`kWh=功率×小时`，金额先算分再变元。有 `tariff_rule` 用谷平峰，否则用站标价。
- **约束**：一用户一条未完成订单、一桩一条充电中（库里部分唯一索引 + 代码检查）。

### 3.5 Database

- **原理**：`QRecursiveMutex` 包住查询/执行。`transaction(fn)`：`fn` 返回 true 才 COMMIT。
- **启动**：`open()` 建表、补列、灌演示账号，不覆盖已有联调数据。
- **协作**：只有 Dispatch 调它写业务；大屏用 Python 只读同一文件（WAL）。

### 3.6 MainWindow / 弹窗

- **原理**：侧栏切页，定时 `refresh()` 拉 Dispatch 的列表和 KPI。按钮只调 Dispatch，再弹 `UiSheet` 显示结果。
- **大屏**：`openDash` 拉起 Flask，浏览器自己读库。

### 3.7 Dashboard / ML

- **大屏**：`findDb()` 找管理端 `data/chargehub.db`；接口失败返回空，不写。
- **预测**：按电站+星期+小时聚合已完成订单；样本少用均值，多样本用简单回归；只 `DELETE/INSERT` 分析表。

## 4. 答辩时容易被问的关系

| 问题 | 答案 |
|------|------|
| 用户端为什么不连库？ | 避免两台电脑各写一份库、对不上账。 |
| 管理端 GUI 为什么不走 8888？ | 和 TcpServer 同进程，再连自己会占第二条连接、也慢。 |
| 推送和轮询为何并存？ | 新客户端用推送；旧客户端只认 `CHARGE_STATUS`，字段不删。 |
| 钱为什么内部用分？ | 浮点累加会差 1 分；接口仍回元，旧客户端不用改。 |
